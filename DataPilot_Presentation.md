# DataPilot - AI-Powered Business Intelligence Platform## University Presentation Report---## 1. Project OverviewDataPilot is a full-stack, AI-powered Business Intelligence (BI) platform that enables users to connect to multiple database systems, write and execute SQL queries, upload and analyze datasets, build interactive dashboards, and leverage AI to convert natural language into SQL. It is built with a modern microservices architecture using Docker, with a FastAPI backend, Next.js frontend, PostgreSQL for persistence, and Redis for caching and task queuing.The platform targets data analysts, business users, and technical teams who need a unified interface for data exploration, visualization, and collaboration without relying on expensive commercial BI tools like Tableau or Power BI.---## 2. Problem StatementOrganizations face several challenges in data analysis workflows:- **Fragmented tooling**: Analysts switch between multiple tools for querying, visualizing, and sharing insights.- **SQL barrier**: Non-technical stakeholders cannot extract data without SQL knowledge.- **Multi-database complexity**: Teams often work with PostgreSQL, MySQL, SQLite, and other databases simultaneously, each requiring different tools.- **Data quality**: Raw datasets (CSV/XLSX) need profiling, cleaning, and validation before they can be analyzed.- **Collaboration gaps**: Sharing queries, dashboards, and insights across teams lacks a structured approach.DataPilot addresses these problems by consolidating query execution, visualization, dataset management, and AI-assisted analysis into a single platform.---## 3. System Operation### Architecture Diagram```User (Browser)    |    v+----------------+       +----------------+|  Next.js 15    |------>|  FastAPI        ||  Frontend      | HTTP  |  Backend        ||  (Port 3000)   |<------|  (Port 8000)    |+----------------+       +--------+-------+                                  |                  +---------------+---------------+                  v               v               v           +------------+ +------------+ +--------------+           | PostgreSQL | |   Redis    | | External DBs |           | (App Data) | | (Cache/    | | (User's DBs) |           |            | |  Celery)   | |              |           +------------+ +------------+ +--------------+                                  |                                  v                           +------------+                           |  Celery    |                           |  Workers   |                           +------------+```### Request Flow1. **Authentication**: User registers or logs in (email/password or OAuth). Backend issues JWT access token (15 min) and refresh token (7 days).2. **Database Connection**: User adds a database connection. Credentials are encrypted with Fernet before storage. Connection is tested via the appropriate adapter.3. **Query Execution**: User writes SQL (manually or via NL2SQL AI). Backend routes the query through the correct database adapter, executes it, and returns columnar results with metadata.4. **Dataset Upload**: User uploads CSV/XLSX. Backend parses the file with Pandas, runs statistical profiling, and stores data in PostgreSQL as a virtual connection.5. **Visualization**: User configures chart type, axes, aggregation, and filters. The frontend generates SQL dynamically, executes it, and renders via Recharts.6. **Dashboard**: User creates dashboards with grid-positioned widgets. Dashboards can be shared publicly via token-based URLs.---## 6. Key Features### 6.1 Multi-Database ConnectivitySupports 9 database types through an adapter pattern: PostgreSQL, MySQL, SQLite, SQL Server, Oracle, MariaDB, MongoDB, Redis, and virtual dataset connections. Each adapter implements schema introspection (list tables, columns) and query execution.### 6.2 AI-Powered NL2SQLConverts natural language questions (e.g., "Show all employees in Engineering with salary above 7000") into executable SQL. Supports OpenAI (GPT-4) and Ollama (local LLM) as providers. Includes conversation history for multi-turn interactions and confidence scoring.### 6.3 Interactive Dashboard BuilderDrag-and-drop grid layout with 5 widget types (chart, text, filter, image, KPI). Supports public sharing via generated tokens and dashboard duplication.### 6.4 16+ Chart Visualization TypesLine, Bar, Pie, Area, Scatter, Funnel, Gauge, KPI, Table, Pivot, Heatmap, Treemap, Sankey, Map, Combo, Donut, and Radar charts.### 6.5 Dataset Management PipelineComplete data workflow: Upload (CSV/XLSX) -> Parse -> Profile (statistics, null counts, distributions) -> Clean (whitespace, type normalization) -> Store (in PostgreSQL) -> Analyze (AI-driven insights and chart suggestions).### 6.6 Chart Builder with Dynamic SQL GenerationVisual chart configuration with column mapping (X/Y axes, group-by), aggregation functions (SUM, AVG, COUNT, MIN, MAX), date hierarchy (Year/Quarter/Month/Day), and filter conditions. SQL is generated dynamically and executed in real-time.### 6.7 Query CollectionsHierarchical folder system for organizing queries. Supports nested subcollections and query assignment during save.### 6.8 Role-Based Access Control (RBAC)Permission-based roles with resource-level sharing (owner/editor/viewer). Admin panel for user management.### 6.9 Collaboration ToolsThreaded comments on resources, version history tracking with snapshots, and dashboard annotations with positional data.### 6.10 Alert SystemCondition-based alerts (threshold, change percentage, anomaly detection) with cron scheduling and notification tracking.---## 7. Project Strengths1. **Modern Architecture**: Follows industry best practices with async FastAPI, React 19, TypeScript, and Docker containerization.2. **Multi-Database Adapter Pattern**: Clean abstraction layer supports 9 database engines without coupling business logic to a specific vendor.3. **AI Integration**: NL2SQL with dual provider support (OpenAI cloud + Ollama local) provides flexibility for different deployment environments.4. **Comprehensive Data Pipeline**: End-to-end workflow from raw file upload to profiled, cleaned, stored, and visualized data.5. **Security Depth**: Fernet encryption for stored credentials, bcrypt password hashing, JWT with refresh rotation, OAuth 2.0 with CSRF state tokens, and RBAC.6. **Dynamic SQL Generation**: The Chart Builder generates SQL dynamically from visual configuration, with proper quoting and injection prevention.7. **Production-Ready Infrastructure**: Docker Compose, Redis caching, Celery background tasks, and Alembic migrations indicate production readiness.8. **Accessibility**: Radix UI primitives ensure WCAG-compliant UI components.9. **Internationalization**: next-intl support for multi-language UI.10. **Collaboration Features**: Comments, version history, annotations, and resource-level permissions go beyond typical BI tools.---## 10. Areas for Improvement1. **Test Coverage**: While pytest is configured, comprehensive unit and integration test suites should be expanded to cover all services and API endpoints.2. **Rate Limiting**: No visible rate limiting on API endpoints, which could lead to abuse in production.3. **Audit Logging**: No dedicated audit trail for sensitive operations (credential access, permission changes, data deletions).4. **Query Result Pagination**: Large result sets are currently limited by a hard cap rather than cursor-based pagination.5. **WebSocket Utilization**: A WebSocket manager exists but real-time features (live dashboard updates, collaborative editing) are not fully implemented.6. **MongoDB/Redis Adapters**: While model types include MongoDB and Redis, the adapter implementations may not be as mature as the SQL adapters.7. **Error Recovery**: Celery tasks lack visible retry policies and dead-letter queue configuration.8. **Performance Monitoring**: No application-level monitoring (APM) integration for production observability.9. **Data Export**: Dashboard export to PDF/image is not implemented.10. **Mobile Responsiveness**: UI is primarily designed for desktop viewport; mobile layout optimization could be improved.---## 11. Final EvaluationDataPilot demonstrates a **strong command of modern full-stack development** and **software architecture principles**. The project successfully integrates a complex technology stack (FastAPI + Next.js + PostgreSQL + Redis + Celery + OpenAI) into a cohesive platform that addresses real business needs.**Architecture Quality**: The adapter pattern for multi-database support, the reducer pattern for chart builder state, and the separation of services/models/schemas in the backend reflect a solid understanding of design patterns.**Technical Depth**: The project goes beyond CRUD operations to implement encryption, OAuth flows, AI integration, dynamic SQL generation, data profiling pipelines, and background task processing.**Practical Value**: This platform solves a genuine problem - providing a self-hosted, open-source alternative to commercial BI tools with AI-powered features that lower the barrier to data analysis.**Overall Assessment**: This is an **advanced-level** project suitable for a senior capstone or graduate-level demonstration. Expert Questions a Professional Evaluator Might Ask### Architecture & Design**Q1: "Why did you choose FastAPI over Django or Flask for the backend?"**> Expected answer: Async support, automatic OpenAPI documentation, Pydantic integration for validation, and better performance for I/O-bound operations like database queries.**Q2: "Explain the adapter pattern you used for multi-database support. How would you add a new database type?"**> Expected answer: Each adapter implements a base interface with `test_connection()`, `get_tables()`, `get_columns()`, and `execute_query()`. Adding a new DB type requires creating a new adapter class and registering it in the factory.**Q3: "Why did you use both Zustand and TanStack Query? Isn't that redundant?"**> Expected answer: TanStack Query handles server state (API data, caching, revalidation), while Zustand handles client-only state (UI preferences, theme, sidebar state). They serve different purposes.### Security**Q4: "How do you prevent SQL injection when users execute raw SQL against their own databases?"**> Expected answer: Users are executing queries against their own connected databases with their own credentials. The platform uses parameterized connections and quotes identifiers in generated SQL. Raw SQL is intentional - the platform is a query tool.**Q5: "What happens if the Fernet encryption key (DB_ENCRYPTION_KEY) is compromised?"**> Expected answer: All stored database credentials would be exposed. Mitigation includes key rotation procedures, storing the key in a secret manager (not .env in production), and limiting access to the encryption key.**Q6: "How does your OAuth implementation prevent CSRF attacks?"**> Expected answer: A signed state token with a 5-minute expiry is generated before redirecting to the OAuth provider. The callback verifies this token before processing the authorization code.### AI Integration**Q7: "How does the NL2SQL feature handle schema context? What are its limitations?"**> Expected answer: The service fetches the database schema (tables, columns, types) and includes it in the prompt to OpenAI/Ollama. Limitations include token limits for very large schemas, potential hallucinations, and inability to understand business-specific terminology without additional context.**Q8: "Why do you support both OpenAI and Ollama? What are the trade-offs?"**> Expected answer: OpenAI provides higher accuracy but requires internet and has cost implications. Ollama enables fully offline, private deployments with no API costs, but typically lower accuracy. The dual-provider approach gives deployment flexibility.### Database & Performance**Q9: "How do you handle long-running queries that might time out?"**> Expected answer: Queries have configurable timeouts (default 30 seconds). The execution is wrapped in a try/catch with proper connection cleanup. Celery workers handle background processing for heavier operations.**Q10: "What caching strategy do you use for query results?"**> Expected answer: Redis is used for caching query execution results. TanStack Query on the frontend provides client-side caching with configurable stale times. The combination reduces redundant database hits.### Data Pipeline**Q11: "Walk me through what happens when a user uploads a 50MB CSV file."**> Expected answer: The file is received by the upload endpoint, parsed with Pandas, profiled (statistics, null counts, top values), optionally cleaned, and then stored in PostgreSQL as a new table. A virtual dataset connection is created so the user can query it like any other database.**Q12: "How does the data profiling work? What statistics do you calculate?"**> Expected answer: For each column: data type, null count, unique count, min/max values, mean, median, standard deviation, and top value frequencies. This helps users understand data quality before analysis.### Deployment & Operations**Q13: "How would you deploy this to production? What would you change from the current Docker Compose setup?"**> Expected answer: Use Kubernetes or managed container services, separate database into managed services (RDS/Cloud SQL), add HTTPS via reverse proxy (Nginx/Traefik), use proper secret management (Vault/AWS Secrets Manager), add monitoring (Prometheus/Grafana), configure CI/CD pipelines, and set up database backups.**Q14: "What is the purpose of Alembic in your project, and how do you handle database schema changes?"**> Expected answer: Alembic manages database migrations as versioned Python scripts. When the SQLAlchemy models change, a new migration is generated and applied to update the database schema without data loss.
